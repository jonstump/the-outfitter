# AGENTS.md

Guide for working in **The Outfitter** — a Hunt: Showdown loadout builder (pick weapons,
equipment, and traits, then save and share builds). Client + API are served as a **single
process on one origin** by design; see Deployment.

## Architecture at a glance

Monorepo using **npm workspaces** (`client/`, `server/`) with a root `package.json`:

```
client/   React 18 + Redux Toolkit + Vite frontend (no typecheck)
server/   Express API + lowdb JSON-file storage
data/     Generated, committed dataset shared by both workspaces (hunters.json)
scripts/  Offline wiki scrapers (never run by dev/build/test/CI)
docs/     ADRs (docs/adrs/) and OpenSpec specs (docs/openspec/specs/)
```

**Data flow (client):** The app is a single-page loadout builder. The in-progress build lives
in a Redux store and is **persisted to localStorage on every loadout mutation** via a module
scope `store.subscribe` in `client/src/store/index.js`. On boot, `App.jsx` hydrates from the
URL hash or localStorage, then fetches saved loadouts / lists / favorites from the API.

**Data flow (server):** Express serves `/api/*` (scoped CORS + JSON body limit `64kb`). The
API is **token-scoped, not auth'd** — every record is owned by a per-browser `x-loadout-token`
header. Three owned collections share the lowdb store: loadouts (`/api/loadouts`), named lists
(`/api/loadout-lists`), and hunter favorites (`/api/hunter-favorites`). Shared ownership
primitives live in `server/src/lib/ownership.js` and MUST stay shared — a divergence across
routers is a cross-user data leak.

## Essential commands

Run from the repo root.

| Command | What it does |
|---|---|
| `npm install` | Install everything. **Enforced** Node major via `engine-strict=true` in `.npmrc` |
| `npm run dev` | Client (Vite :5173, proxies `/api`→:4100) + server (:4100) concurrently, watch mode |
| `npm test` | **The whole suite** — client, server, and scrape scripts. This is exactly what CI runs. Always run this, not just one workspace |
| `npm test -w client` | Client vitest only (jsdom) |
| `npm test -w server` | Server vitest only. Sets `OUTFITTER_DB_FILE` to a throwaway file |
| `npm run test:scrape` | Scrape-script tests only (`node --test scripts/*.test.mjs`) |
| `npm run build` | Production client build (`vite build`) |
| `npm start` | Production server: serves the built client from `client/dist` and the API on `PORT` (default 4100) from **one origin** |
| `npm run build -w client` | Client build (CI also runs this separately) |

There is **no lint and no type-check** in this repo — nothing to run. The tests are the gate.

**CI runs the equivalent of `npm test`** and additionally: verifies `package-lock.json` is in
sync with the manifests (`npm install --package-lock-only`), builds the client image and boots
it to smoke-test the packaged layout, and asserts npm refuses an unsupported Node major. So a
passing `npm test` locally is necessary but **not sufficient** — the lockfile-sync and Docker
layout checks are CI-only.

## Node version / toolchain

- Canonical pin is `.nvmrc` → `lts/iron` (Node 20, Iron). `engines.node` + `engine-strict` make
  installs **fail on a wrong major** rather than warn.
- `mise.toml` is an optional convenience layer mirroring the pin (numeric major `20`, npm `10`).
- **Never hand-edit the lockfile** in a way that desyncs it from manifests; CI fails on any
  lockfile drift. `npm install --package-lock-only` is the sanctioned way to reconcile.
- `.npmrc` also sets `engine-strict=true` — this is the enforcement point, don't remove it.

## The generated datasets (never hand-edit)

Three committed, generated artifacts are written only by the offline scrape scripts and must
not be hand-edited (upstream documentation even says "Generated files are committed and must
not be hand-edited; re-running the scrape rewrites them"):

- **`data/hunters.json`** — the hunter roster, at the **repo root** (not in `client/`). The
  server's prod image needs it to validate favorited hunter ids and **refuses to boot without
  it**. Generated by `node scripts/scrape-hunters.mjs`. Vite bundles it into the client via
  `client/src/data/hunters.js`, which just re-exports `../../../data/hunters.json`. The other
  `client/src/data/hunters.*` files are hand-authored exports (favorites lookup, thumbnails).
- **`client/src/data/itemStats.json`** — one stats record per catalog item, keyed by catalog id.
- The `client/public/images/` tree — catalog item art + hunter AVIF portraits.

Scrape scripts respect `robots.txt`, rate-limit, and are never run by dev/build/test/CI. Only
run them by hand to refresh data: `scrape-images.mjs`, `scrape-hunters.mjs` (see `--names-only`
to skip `sharp`; every AVIF portrait has a **byte budget** — an over-budget asset fails its
hunter), `scrape-stats.mjs` (`--write-catalog` reconciles `catalog.js`; default is additive and
never touches `catalog.js`). Tests for them are `*.test.mjs` beside each script.

## The catalog (`client/src/data/catalog.js`) — read this before editing pools

The game catalog is a set of **tuple arrays** (`WEAPONS`, `TOOLS`, `CONS`, `TRAITS`, `AMMO`).
Style/rules that matter a great deal:

- **Items are referenced by stable slug `id`, never by array position.** The wire format
  (`utils/loadoutCodec.js`), localStorage, saved loadout records, and share URLs all key on
  `id`. Reordering/inserting/removing entries is safe **only** because ids are stable.
- **`AMMO` is the one exception and the closest thing to a foot-gun in this codebase.** A saved
  ammo selection persists as a **bare index into `AMMO[ammoClass]`**. Inserting/removing/
  reordering a variant inside a pool silently re-points every saved selection in that class,
  and **nothing errors** — the cost line just changes. Appending to the END of a pool is the one
  safe edit. Any other edit needs a `FORMAT_VERSION` bump + saved-selection migration, on the
  same terms as changing a weapon's `ammoClass`. This is spelled out in a WIRE-FORMAT GATE
  comment at the top of the file — read it.
- `AMMO` is **never written by a scrape** (wiki has no per-pool source page).

## The loadout wire format (`client/src/utils/loadoutCodec.js`)

- `FORMAT_VERSION = 3` (ADR-0023). Bump it when `toData()`'s shape changes so `fromData()` can
  migrate old encodings instead of misreading them. A version-3 weapon entry is
  `[weaponId, ammoIndex, d]` — the third element is the dual-wield pair flag, always a
  boolean on the wire. Decoders are selected by declared version; v2/v1/legacy records still
  decode with no pair flag at all (they could not express one).
- Equipment is a **fixed eight-cell sparse grid**: `e` is a length-8 array where **index IS the
  cell and `null` IS an empty cell**; `b` is an array of blocked cell indices. This is
  ADR-0009. A removal empties only that cell — never a packed `splice`.
- **Every weapon in loadout STATE carries a boolean `d`**, normalized at the reducer boundary
  (`addWeapon`, `setLoadout`) rather than in the decoders — the decoders deliberately return
  `d`-less weapons for pre-v3 records. Pairability is read from the scraped itemStats
  attribute (`dualWieldFor`, never derived from size/name). A pair costs `size + 1`
  (`weaponSize` in `utils/calc.js`) and doubles only the weapon's price in `totalCost`.
- **Decoders clamp rather than throw.** The store's localStorage `subscribe` persists a decoded
  loadout *before* it is rendered, so a decoder that refused would write the very record it
  rejects and then fail on it on every visit. Bounds like the ammo-variant index and the
  15-trait cap are applied in the decoder (`boundedAmmo`, `boundedTraits`) so nothing bad can
  persist.
- Loadout shape invariants (fixed capacities) are also validated by `loadoutSlice.js`
  (`isValidLoadoutShape`) and all cost/capacity predicates live once in `utils/calc.js`
  (`TRAIT_MAX = 15`, `capMax`, `consAllowed`, `hasFreeCell`, `heldItems`, `weaponSize`) — **import
  these rather than re-deriving a bound**. The reducer, picker, generator, and both decoders all
  consult the same predicates so they cannot drift apart.

## Governing comments convention (strong, pervasive)

Nearly every file carries block comments like:

```
// Governing: ADR-0006 (chose JWT over sessions), SPEC-0003 REQ "Token Validation"
```

There are **267 `// Governing:` comments** in `client/src` + `server/src`. When you write code
governed by an ADR or spec, add a matching reference comment. When a decision was made in a PR
or issue (e.g. `issue #20`), those get cited inline too. This is how `/sdd:check` traces
implementation → design artifacts, so keeping them current is part of the work. If you change
behavior, update the comment that governed it.

## Tests: approach and gotchas

- Framework is **Vitest** throughout (there is deliberately no Jest). Client uses `jsdom`
  globals + jest-dom matchers from `client/src/test/setup.js`; server uses supertest against a
  **real lowdb JSONFile store, never a mock**.
- **Server must not run parallel** — `server/vitest.config.js` sets `fileParallelism: false`
  on purpose. Every suite shares ONE lowdb data file, and lowdb's read-modify-write cycle
  corrupts under concurrency. Do not "help" by removing it.
- **Never import the real app store in tests.** The real `client/src/store/index.js` has a
  module-scope `store.subscribe` that persists to localStorage. Use
  `createTestStore()` from `client/src/test/testStore.js`, which builds a fresh store from the
  same slice reducers without that side effect.
- `client/src/test/setup.js` stubs `scrollIntoView` and adds a minimal `PointerEvent` — jsdom
  lacks both. The `PointerEvent` stub is load-bearing for the equipment-grid touch-drag branch
  (`pointerType`). It is emphatically NOT a substitute for real-browser testing.
- Test files sit **next to the code they test** with the same basename (`Foo.jsx` /
  `Foo.test.jsx`, `bar.js` / `bar.test.js`). Server route tests are `*.test.js` in the same
  `routes/` dir.
- Server `db.test.json` explicitly exercises the real store; the working files
  `db.cors-test.json` / `db.direct-test.json` exist because `index.test.js` boots real child
  processes. All are gitignored.

## Storage & the single-writer constraint (deployment-critical)

All saved state is one **lowdb JSON file**: `server/data/db.json` (`OUTFITTER_DB_FILE`
overrides the path; dev file is gitignored). lowdb is a **single-process, single-writer**
store. Consequences you must respect:

- **One instance only** in any deployment. Two replicas fork the data file and silently
  diverge. `render.yaml` forces `numInstances: 1` and a **persistent disk** mounted at
  `/app/server/data` — ephemeral/dirty storage wipes every saved loadout on redeploy.
- The Dockerfile's runtime stage mounts `/app/server/data` as a `VOLUME` and must `COPY data`
  (the roster) into the runtime stage — multi-stage builds discard the build stage's files in a
  `client/src`, which silently broke favorites before.

### `TRUST_PROXY` — the single most dangerous env var

Which peers the server believes `X-Forwarded-*` from; decides `req.protocol`, `req.ip`, and the
X-Forwarded-Host lookup behind the same-origin check (both rate limiters key on `req.ip`).
Configure it in the **deployment**, never hardcode:

| Topology | Setting |
|---|---|
| `docker compose up`, Procfile VM, nothing in front | leave **unset** |
| Proxy on same host (nginx, Caddy) | `TRUST_PROXY=loopback` |
| Proxy elsewhere | `TRUST_PROXY` to its address/CIDR |
| Managed platform that terminates TLS (Render, Fly) | `TRUST_PROXY=1` |

- Leave unset behind a TLS-terminating proxy and the app loads but **every write 403s** ("loads
  fine, nothing saves"). This has actually happened in production (on Render).
- Setting `TRUST_PROXY=true` is **refused at boot on purpose** (`lib/trustProxy.js`) — Express
  boolean `true` trusts everyone at every hop. Name the proxy.
- `docker-compose.yml` deliberately has no `TRUST_PROXY` (port published straight to host).

## Client component & state organization

- Components are feature-foldered under `client/src/components/<Name>/` with a
  `<Name>.{jsx,test.jsx}` pair per unit (e.g. `TraitsPanel/`, `Picker/`, `EquipmentPanel/`).
- Redux state is split into slices in `client/src/store/`: `loadoutSlice`, `uiSlice`,
  `savedLoadoutsSlice`, `loadoutListsSlice`, `hunterFavoritesSlice`, plus `selectors.js`,
  `thunks.js`. The `data/` dir bundles the catalog; `utils/` holds the pure game logic
  (`calc.js`, `loadoutCodec.js`, `randomize.js`, `slugify.js`, `stacking.js`, `focusTrap.js`,
  `listOrdering.js`, `listAccent.js`).
- **Pure game logic is extracted into `utils/` and unit-tested directly** (no React/DOM). The
  strongest cross-cutting invariants (budget math, caps, capacities, wire format) live there,
  so a change to a gameplay rule usually means changing `calc.js` / `loadoutCodec.js` /
  `randomize.js` and their tests.
- The loadout randomizer (`utils/randomize.js`) obeys the same capacity predicates as the
  reducer, budget retries with a guard count, and generates a well-formed fixed grid (SPEC-0006/
  SPEC-0008).

## Key non-obvious gotchas

- **`client/src/data/hunters.js` re-exports the root `data/hunters.json`**; perpendicular
  files (`hunterFavorites.js`, `hunters.js` roster consumers) are hand-authored. Don't confuse
  the generated dataset with its consumers.
- **`scraped-image` lookups derive URL from the item slug** (`ItemThumb.jsx`) via `onError`
  chain, falling back to SVG icons. There's no generated IMAGES manifest to keep in sync.
- **`hunterId` absent from the dataset is valid** (retired/never scraped) — consumers must
  tolerate `null` for unknown ids (SPEC-0003/SPEC-0004).
- **Capacity/lists accent assignment:** accent colors are assigned server-side
  (`loadoutLists.js` `nextAccent` + palette) and mirrored by `client/utils/listAccent.js` —
  keep the client mirror in step.
- Wire-format payloads are **allowlisted server-side**: a body carrying any key outside the
  defined format is refused rather than persisted.

## Docs: ADRs and OpenSpec specs

This project uses the [SDD](https://github.com/joestump/claude-plugin-sdd) workflow:
decide → `/sdd:adr`, specify → `/sdd:spec`. `docs/adrs/` holds 23 MADR-format ADRs, and
`docs/openspec/specs/` holds 10 specs (`SPEC-0001`…`SPEC-0010`). Before changing behavior,
look up the governing ADR/spec and add a `// Governing:` comment. The README "Project
structure" and deployment sections are authoritative and detailed; `.env.example` documents
every env var with extensive rationale — read it before touching env handling.
